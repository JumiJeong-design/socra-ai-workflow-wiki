# 에이전트 핸드오프 플레이북

## 언제 사용하나

작업을 새 세션이나 다른 에이전트에서 이어갈 가능성이 있을 때 사용한다. 현재 운영 모드는 Claude Code 단일 에이전트이므로(2026-07-13~), 실제 핸드오프는 대부분 **세션 간**에 일어난다. 컨텍스트가 끊긴 다음 세션이 repo 문서만 보고 이어갈 수 있게 만드는 것이 목적이다.

이 플레이북은 대화 내용을 전부 기록하기 위한 문서가 아니다. 다음 에이전트가 이미 끝난 일을 반복하거나, 작업 날짜를 잘못 옮기지 않고, 올바른 문서에서 바로 시작하게 만드는 절차다.

## 핵심 규칙

핸드오프는 다음 에이전트가 repo 문서만 보고 아래 세 질문에 답할 수 있을 때 완료다.

1. 이미 완료된 작업은 무엇인가?
2. 다음에 해야 할 작업은 무엇인가?
3. 에이전트가 할 일이 아니라 주미님 확인이 필요한 작업은 무엇인가?

답이 채팅 안에만 있고 repo 문서에 없으면 핸드오프가 완료된 것이 아니다.

계획과 승인은 분리한다. worklog, plan, backlog에 적힌 항목은 다음에 볼 후보이지, 피그마나 코드에 바로 write해도 된다는 뜻이 아니다. 특히 시각 방향, 화면 톤, 공통 컴포넌트 스타일처럼 주미님 판단이 필요한 변경은 read-only 감사와 명시 승인을 거친 뒤 실행한다.

`CONTEXT.md`는 세션 스냅샷이다. 최신 worklog나 원격 git 상태보다 오래됐으면 현재 상태로 믿지 않고, 최신 worklog, 공개 viewer, 관련 repo의 `git status -sb`와 최근 커밋을 먼저 확인한다.

## 진입 문서

| 표면 | 역할 |
| --- | --- |
| product repo `CLAUDE.md` 또는 `AGENTS.md` | 작업 repo에서 AI 에이전트가 처음 읽는 파일 |
| product plan / follow-up 문서 | 다음 기술 작업의 현재 기준 문서 |
| `jumi-worklog/CONTEXT.md` | 여러 repo를 가로지르는 세션 스냅샷과 다음 작업 분리 |
| `jumi-worklog/logs/YYYY/MM/YYYY-MM-DD.md` | 날짜별 작업 기록과 체크리스트 상태 |
| 공개 `site/worklog.html` | 주미님이 브라우저에서 직접 확인하는 화면 |

## 반드시 분리할 것

모든 핸드오프는 아래를 분리해야 한다.

| 유형 | 의미 |
| --- | --- |
| 에이전트 작업 | 에이전트가 문서화된 근거를 보고 이어갈 수 있는 작업 |
| 주미님 확인 | 시각 판단, 로그인 세션이 필요한 QA, 제품 방향, 승인 결정 |
| 이월 작업 | 의도적으로 다음 날짜나 후속 범위로 넘긴 작업 |

다음날 할 일을 완료된 작업 섹션 안에 넣지 않는다. 해당 날짜의 `Next` 또는 다음 날짜 worklog에 둔다.

## 완료 정의

source만 바뀐 상태는 완료가 아니다. 특히 토큰이나 공개 CSS 변수 변경은 생성물과 정적 Storybook에 반영됐는지 확인해야 다음 세션이 같은 문제를 다시 추적하지 않는다.

완료는 source 변경, 생성물 반영, Storybook/Chromatic 확인, worklog/plan 반영을 모두 포함한다.

## (휴면) 병렬 작업 핸드오프 — 두 에이전트 동시 진행 시

제2 에이전트(Codex 등)를 다시 병행할 때만 적용하는 휴면 규율이다. 현재 운영 모드는 Claude Code 단일 에이전트이므로 이 절은 활성이 아니다. 같은 세션 안에서 병렬이 필요하면 별도 에이전트 구독이 아니라 **Claude Code 서브에이전트 + `git worktree` 격리**를 사용한다(팬아웃 3~4개 소규모 기본).

여러 에이전트가 같은 repo를 나눠 작업할 때는 다음 항목이 문서에 없으면 병렬 작업으로 시작하지 않는다.

| 항목 | 기록할 내용 |
| --- | --- |
| worktree / branch | 각 트랙이 사용하는 로컬 경로와 브랜치 |
| 소유 범위 | 디렉터리, 컴포넌트, 토큰, Storybook 영역 중 무엇을 누가 만지는지 |
| 생성물 owner | `theme.css`, `public.manifest.json`, 정적 Storybook 산출물처럼 빌드로 갱신되는 파일의 단일 소유자 |
| 머지 순서 | foundation/token, component, Storybook/QA 중 어떤 트랙이 먼저 머지되어야 하는지 |
| 재생성 금지 파일 | owner가 아닌 트랙이 검증 중 생성해도 커밋하면 안 되는 파일 |
| 완료 정의 | source 변경, 생성물 반영, Storybook/Chromatic 확인, worklog/plan 반영 여부(위 `완료 정의` 참고) |

## 팬아웃 소유권 규칙 — 서브에이전트 병렬 시

병렬은 "무엇을 나누냐"가 아니라 "소유권을 어떻게 자르냐"의 문제다. 네 트랙 모두를 같은 불안정한 외부 의존(MCP 연결)에 걸어 뒀다가 3시간 반을 통째로 잃은 날과, 소유권 경계를 프롬프트에 박아 트리 충돌 0으로 끝난 날의 차이는 분할 설계였다.

- 갈래마다 쓰기 대상(트리·파일·파일 영역)을 배타적으로 지정한다. 예: ① 배포 스파인(메인 트리 소유) ② 코드 작업(worktree 격리) ③ read-only 감사.
- 불안정한 외부 의존(MCP 등)을 타지 않는 트랙을 최소 하나 둔다 — 의존이 죽어도 세션 전체가 헛돌지 않는다.
- 착수 시 각 세션이 자기 트랙명을 1회 선언한다 — 실제로 샌 곳은 코드가 아니라 세션 호칭이었다.

## 공유 워킹트리 규율

같은 폴더에 두 세션이 붙으면 반드시 사고가 난다 — 다른 세션이 브랜치를 갈아타 체크아웃이 통째로 바뀐 사건이 네 번 반복됐다. 소유권을 물어봐도 무응답이 기본이므로, 기다리지 말고 `git worktree`로 격리한다.

- 커밋 전 `git status -sb`로 현재 브랜치를 확인한다.
- 파일을 명시해 스테이징한다. `git add -A` 금지 — 남의 미커밋 파일이 내 커밋에 딸려 들어온다.
- 되돌릴 땐 `git checkout -- <file>`이 아니라 내가 넣은 텍스트만 역치환한다 — checkout은 남의 미커밋 작업을 날린다.
- 머지는 로컬 체크아웃이 아니라 서버 쪽(`gh`)에서 한다.
- 착수 전 최근 머지 이력을 먼저 조회한다 — "미착수"로 보고된 항목이 이미 피어에게 머지돼 있던 적이 있다.

## 진행 순서

1. 최신 worklog와 현재 product plan을 읽는다.
2. `CONTEXT.md`가 최신 worklog보다 오래됐는지 확인한다. 오래됐으면 stale snapshot으로 표시하고 최신 git 상태를 우선한다.
3. 계획 항목 중 실행 승인 없이 write하면 안 되는 항목을 분리한다.
4. 완료됐지만 아직 unchecked인 항목을 찾아 즉시 체크한다.
5. 체크리스트에 없던 일을 완료했다면 새 체크 항목을 추가하고 `[x]`로 표시한다.
6. 다음 에이전트가 올바른 문서와 섹션에서 시작하도록 product repo 진입 문서를 갱신한다.
7. product follow-up 문서는 이미 끝난 일이 아니라 다음에 할 일을 말하도록 갱신한다.
8. `CONTEXT.md`에는 현재 상태와 에이전트 작업 / 주미님 확인 분리를 반영한다.
9. 공개 `site/worklog.html`에도 같은 worklog 내용을 반영한다.
10. 로컬 파일만 보지 말고 공개 URL을 직접 받아 화면에 보이는 내용을 확인한다.

## 공개 검증

worklog를 바꿨다면 로컬 markdown만으로는 완료가 아니다.

필수 확인:

- 원본 `jumi-worklog` markdown이 갱신되어 있다.
- 공개 `site/worklog.html`이 갱신되어 있다.
- 두 repo가 모두 commit/push되어 있다.
- 공개 URL에서 새 내용이 보인다.
- 월 단위 worklog 검증이 통과한다.

오늘 entry만 맞아 보여도 오래된 `plan-*` 블록이나 과거 unchecked 항목이 공개 화면에 남을 수 있으므로 월 단위 검증을 사용한다.

## 하지 말 것

- 커밋, 회고, 다음 액션을 기록하려고 새 H2를 만들지 않는다.
- 날짜 안의 `###` 메모로 충분한 내용을 별도 탭으로 만들지 않는다.
- 원래 계획에 없던 일이라는 이유로 완료 작업을 unchecked 상태로 두지 않는다.
- 이미 존재하는 audit 표를 다시 만들지 않는다. 표를 링크하고 다음 액션부터 이어간다.
- 공개 페이지를 직접 받아 확인하기 전에는 "배포 완료"라고 말하지 않는다.
- plan/worklog 항목을 피그마 write 승인으로 해석하지 않는다.
- stale `CONTEXT.md`만 믿고 현재 상태를 보고하지 않는다.

## 완료 기준

- 다음 에이전트 진입 파일이 현재 기준 문서를 가리킨다.
- 현재 product plan에 명확한 다음 액션 handoff가 있다.
- worklog 체크박스가 실제 상태와 맞다.
- 에이전트 작업과 주미님 확인 작업이 분리되어 있다.
- 실행 승인 없이 write하면 안 되는 피그마/코드 작업이 분리되어 있다.
- `CONTEXT.md` 최신성 또는 stale 여부가 확인되어 있다.
- 공개 worklog URL에 같은 내용이 보인다.
- 월 단위 공개 worklog 검증이 통과한다.
