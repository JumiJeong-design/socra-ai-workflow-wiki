# 완료 기준 플레이북: 1차 / 공유 가능 / 픽스

## 언제 사용하나

에이전트가 "완료"라고 보고했는데 디자이너 눈에는 남은 일이 보일 때, 그리고 팀에 화면 일정을 말해야 할 때 사용한다. 2026년 8월에 규칙으로 정했고 이후 에이전트 보고 형식으로 쓰고 있다.

## 왜 완료를 나누나

에이전트의 "완료"와 디자이너의 "완료"가 다르다. 에이전트는 기획과 구조가 그려지면 끝났다고 보고 디자이너 기준으로는 시각 품질과 UX 검토가 남아 있다. 이 간극 때문에 남은 일이 어디에도 기록되지 않은 채 사람 머릿속에만 쌓인다.

일이 도착하는 모양도 바뀌었다. 기획→디자인→개발→QA로 한 번에 하나씩 오던 구조에서, 화면 설계·컴포넌트·문서·QA 준비가 에이전트 완료 시점에 동시에 도착하는 구조가 됐다. 검수 1명 앞에 큐가 생기고 열어보기 전에는 10분짜리 확인인지 2시간짜리 재작업인지 모른다. "이 화면 2.5일" 같은 점 추정은 순차 전제에서만 성립한다.

## 3단계

| 단계 | 뜻 | 누가 선언 | 공유 |
| --- | --- | --- | --- |
| `1차` | 기획·구조가 그려짐 | 에이전트 | 공유하지 않음 |
| `공유 가능` | 구조·방향이 섬. 디테일은 미픽스 | 에이전트 자가 검사 → 디자이너 확인 | 팀 공유 OK |
| `픽스` | 품질·UX 검토 끝 | 디자이너만 | 변경 시 공지 |

기존 Figma 화면 상태와 같은 사다리다. `공유 가능` ≈ `candidate`, `픽스` ≈ `approved screen`.

## 에이전트 보고 규칙

- "완료"를 단독으로 쓰지 않는다. 항상 단계명으로 보고한다.
- `1차 완료. 남은 것: 시각 품질, UX 흐름`처럼 남은 단계를 문장으로 남긴다.
- `공유 가능`은 아래 기준을 자가 검사하고 결과를 보고에 붙였을 때만 선언한다.
- `픽스`는 에이전트가 선언할 수 없다. 준비만 한다.

## 공유 가능 기준

하나라도 빠지면 `공유 가능`으로 부르지 않는다.

1. **목적 한 문장**: 이 화면이 해결하는 사용자 목적
2. **핵심 흐름·분기**: IA와 사용자 분기가 정의됨
3. **DS 준수**: 승인된 컴포넌트·인스턴스만 사용. 손코딩 0
4. **핵심 상태**: 그 화면에 필요한 상태가 있음 (empty/loading/error 전체 강제는 아님)
5. **출처 근거**: Figma node id·variables 또는 패키지 계약. 없으면 `pending`으로 두고 추측하지 않는다
6. **미결 질문 분리**: 디자이너 판단이 필요한 항목이 목록으로 뽑혀 있음
7. **공유 라벨**: `구조·플로우 픽스 / 비주얼·디테일 미픽스`처럼 무엇이 픽스인지 명시

문구는 lorem만 아니면 된다. 확정 문구는 `픽스` 몫이다.

## 픽스 기준

디자이너 판단이다.

1. **UX 흐름**: 사용자가 주요 행동을 바로 찾는가
2. **시각 품질**: 위계·밸런스·브랜드 톤
3. **토큰 준수**: spacing·typography·color 임의값 0
4. **QA 축**: 전 축이 아니라 그 컴포넌트의 리스크 우선 축만. 축 정의는 [AX 매뉴얼 11장](../manual/11-five-channels-publish-gate.md)에 있다
5. **실제 도는 표면에서 확인**: 컴포넌트 안은 Storybook, 화면 밖은 앱
6. **승인 기록**: 승인 대기와 승인 완료를 구분해 기록

## 일정은 두 날짜로 말한다

- **공유 가능일**은 예측 가능하니 팀에 약속한다. 이 날 FE 착수와 리뷰가 시작되고 디자이너 품질 검토는 그 뒤로 병렬 진행한다.
- **픽스일**은 AI 품질 편차와 진행 중 발견되는 범위 때문에 구간으로만 말하고 진행하며 갱신한다.
- 날짜가 박힌 일은 처음부터 병렬 밖으로 빼서 순차로 처리한다.
- 공유할 때 라벨을 빼면 미픽스 디테일에 피드백이 쏟아져 부하가 오히려 늘어난다.
