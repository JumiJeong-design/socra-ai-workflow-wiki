# 사례: 이름은 같은데 값이 달랐다

> 구분: 사례 · 기간: 2026-08 ~ 09-21 · 관련: [매뉴얼 12장 시각 기준](../manual/12-visual-baseline.md), [23장 DS → 스토리북 계약 정리](../manual/23-prompt-ds-storybook-contract.md)

피그마와 코드의 색 토큰을 이름으로 대조해서 「맞다」고 판정하는 경우의 사례다. 회색 이름이 같은데 값이 달랐다. 이름으로 대조하면 맞아 보이고 값으로 대조하면 틀렸다. 같은 사고가 두 번 났다.

## 한눈에

| 날짜 | 무슨 일 | 뒤집힌 것 | 그래서 |
|---|---|---|---|
| 8~9월 | 회색 이름이 한 칸 밀려 있었다 | 이름은 라벨, 값이 실물 | 대조는 값으로 |
| 8~9월 | 색 변수가 두 세대로 살아 있었다 | 라이트 값이 같아 다크만 다른 게 안 보였다 | 라이트·다크 둘 다 값으로 |
| 9/7 | 문서에 「다크 값 없음」 | 램프 80칸에 다크 값이 다 있었고 코드가 4칸만 가져왔다 | 문서보다 마스터를 직접 잰다 |
| 9/7 | 램프에 칸을 하나 끼운 뒤 「어긋난 자리 넷」 | 셋은 오판. semantic을 거친 자리는 자동으로 따라왔다 | 직접 물지 말고 semantic을 거치게 |
| 9/8 | 옛 세대 변수 46곳 | 원천에서 끊고 이관을 닫았다 | 두 세대 정리 완료 |
| 9/21 | 램프 번호를 직접 문 토큰 42개 | 칸을 끼울 때 2주 동안 옛 값에 남아 있었다 | 직접 문 자리를 주기적으로 센다 |

## 원인과 처방

| 원인 | 처방 |
|---|---|
| 이름은 사람이 붙인 라벨이고 값은 실물이다 | 대조는 값으로. 라이트·다크 둘 다 |
| 라이트 값이 같으면 다크 값 차이가 안 보인다 | 두 모드를 항상 같이 잰다 |
| 레포 문서는 마스터보다 늦게 갱신된다 | 정합 판정은 피그마 변수와 마스터를 직접 재서 한다. 문서와 다르면 문서가 낡은 것으로 보고 그 줄도 고친다 |
| 램프 번호를 직접 물면 램프가 움직여도 안 따라온다 | 램프를 직접 물지 말고 semantic을 거치게 한다 |
| 원인을 한 사례로 단정해 문서 세 곳에 퍼뜨렸다 | 「어긋났다」고 적기 전에 그 자리가 무엇을 거쳐 값을 받는지 본다 |

## 직접 해 보려면

```text
피그마 [변수 컬렉션 이름]과 코드 [토큰 파일 경로]를 대조해 줘. 이름이 아니라 값으로 비교하고, 라이트·다크 두 모드 다 봐.
이름은 같은데 값이 다른 것, 값은 같은데 이름이 다른 것을 두 표로 나눠. 레포 문서에 「없다」고 적혀 있어도 피그마 변수를 직접 세서 확인하고, 다르면 문서 줄도 같이 고쳐.
```

```text
[소비 파일 이름]에서 같은 이름의 색 변수가 몇 벌 있는지 세 줘. 둘 이상이면 각 벌의 라이트·다크 값과 그 벌을 무는 자리 수를 표로.
옛 세대를 무는 자리는 목록만 보여 주고, 내 승인 전에는 바꾸지 마.
```

```text
[램프 이름]의 값을 바꾸려고 해. 바꾸기 전에 그 램프 번호를 직접 무는 자리(semantic을 거치지 않는 것)를 피그마와 코드 양쪽에서 세 줘.
직접 문 자리는 램프가 움직여도 안 따라오니까, 그 목록을 먼저 보여 주고 어느 것을 semantic으로 옮길지 정한 뒤 값을 바꿔.
```

```text
어긋났다고 보고할 자리마다 그 자리가 값을 어디서 받는지(램프 직접 / semantic 경유 / 손으로 박은 값) 같은 줄에 적어.
semantic을 거치는 자리는 값이 따라왔을 수 있으니 마스터를 열어 실제 값을 확인한 뒤에 어긋났다고 적어.
```
