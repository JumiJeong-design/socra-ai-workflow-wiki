# 사례: 규칙이 879줄 있는데 같은 실수가 났다

> 구분: 사례 · 기간: 2026-08-25 ~ 09-17 · 관련: [매뉴얼 13장 행동 기준](../manual/13-behavior-baseline.md), [20장 하네스](../manual/20-harness.md), [31장 이 방식의 단점](../manual/31-principle-costs.md)

AI가 실수할 때마다 규칙을 한 줄씩 적는데, 규칙이 있는데도 같은 실수가 반복되는 경우의 사례다. 두 달 만에 규칙이 51개 879줄이 됐고, 게시와 수락을 가르는 규칙은 본문이 있었는데도 열흘간 같은 오판이 반복됐다. 「규칙을 왜 안 읽나」가 아니라 「규칙이 왜 안 읽히나」가 문제였다.

## 한눈에

| 날짜 | 무슨 일 | 뒤집힌 것 | 그래서 |
|---|---|---|---|
| 8/25 | 열흘 반복된 오판의 규칙이 이미 있었다 | 규칙이 없어서가 아니라 다른 규칙 밑에 묻혀 있었다 | 규칙 본문 대신 「이럴 때 → 몇 번」 색인을 매 세션 읽히는 파일에 |
| 9/2 | AI가 같은 실수를 하루 세 번 하고 규칙을 하나 더 썼다 | 규칙을 늘리면 읽힐 가능성이 줄어든다 | 커밋 직전 자동 검사로. 그날 작동한 건 전부 자동으로 뜬 것 |
| 9/8 | 지침 문구를 다시 쓰고 있었다 | 「하지 말라」고 적힌 명령을 아홉 번 실행했다 | 실행 직전에 막는 훅 셋 |
| 9/10~17 | 훅 헛걸림을 재측 | 40% → 37.5%, 목표 20%에 못 미침. 훅 파일도 낡아 있었다 | 넓히지 않고 닫음. 훅도 유지 비용이 있다 |

색인표는 이런 모양이다. 체크리스트가 아니라 색인이라 절차를 강요하지 않고 판단은 남긴다.

| 이럴 때 | 볼 것 |
|---|---|
| 뭔가 새로 만들려 할 때 | 「이미 있나」 규칙 |
| 게시·전파를 판정할 때 | 「게시 ≠ 수락」 규칙 |
| 검사 결과가 「0개」로 나올 때 | 「0건이면 범위를 적는다」 규칙 |

훅 셋은 이렇다.

| 언제 | 무엇을 |
|---|---|
| 명령 실행 직전 | 공유 폴더에서 위험한 git 명령 여덟 가지를 막는다. 격리된 작업 폴더에서는 안 막는다 |
| 세션 시작 | 지금 폴더가 공유 폴더인지, 남은 커밋과 열린 항목이 몇 개인지 첫 화면에 띄운다 |
| 커밋 직전 | 패키지 코드를 바꿨는데 변경 기록이 없으면 막는다 |

## 원인과 처방

| 원인 | 처방 |
|---|---|
| 규칙은 읽어야 작동하고, 읽는 데는 비용이 든다 | 규칙 본문은 따로 두고, 매 세션 읽히는 파일에는 「이럴 때 → 몇 번」 색인만 둔다 |
| 검색은 찾을 단어를 이미 알 때만 걸린다 | 색인은 증상 이름으로 건다. 규칙마다 처음부터 번호와 「이럴 때 본다」 한 줄을 붙인다 |
| 규칙은 알고도 어긴다. 읽기 문제가 아니라 막기 문제다 | 같은 실수가 두 번 나면 규칙을 더 적지 말고 실행 자리에서 막는다 |
| 규칙을 늘리면 읽힐 가능성이 줄어든다 | 규칙을 늘리자는 제안이 오면 「1번부터 매번 읽다가 놓치는 거 아니야?」를 먼저 묻는다 |
| 헛걸리는 게이트는 우회가 습관이 되어 죽는다 | 게이트는 실제 이력으로 재서 좁힌다. 목표(20% 아래)에 못 미치면 넓히지 않는다 |
| 훅도 낡는다 | 훅 파일이 작업 폴더마다 같은 판인지 가끔 확인한다 |
| 발견·결론까지 체크박스로 적으면 열린 항목이 부푼다 | 체크박스는 「누가 손대면 닫히는 일」에만. 대기 사유에는 「무엇이 어떻게 되면 풀리는지」를 같은 줄에 |

## 직접 해 보려면

```text
[규칙 문서 경로]에 있는 규칙마다 번호가 있는지 확인하고, 없으면 붙여 줘.
규칙마다 「이럴 때 본다」 한 줄을 추가해. 규칙 제목이 아니라 증상으로 적어. 「게시 ≠ 수락」이 아니라 「수락했는데도 안 바뀔 때」처럼.
바꾼 뒤 「이럴 때 → 번호」 표로 모아서 보여 줘.
```

```text
[규칙 문서 경로]의 본문은 CLAUDE.md에 넣지 말고, 「이럴 때 → 규칙 번호」 표만 만들어서 넣어 줘.
표 한 줄에 상황 하나, 증상 이름으로. 표가 [기준, 예: 30줄]을 넘으면 어느 줄을 합칠지 먼저 물어.
```

```text
[실수 내용]이 두 번째야. 규칙을 더 적지 말고, 실행 직전이나 커밋 직전에 자동으로 막을 수 있는지 먼저 봐 줘.
막을 수 있으면 어느 자리(명령 실행 직전·세션 시작·커밋 직전)에 무엇을 만들지 한 줄로 제안하고 내 승인을 받아. 못 막으면 왜 못 막는지 적어.
```

```text
[검사 이름]이 지난 커밋 [개수, 예: 40개]에 걸었으면 몇 줄이 걸렸을지 재 줘. 걸린 줄마다 진짜 문제였는지 헛걸림이었는지 표로 나눠.
헛걸림이 [기준, 예: 20%]를 넘으면 패턴을 좁히고 다시 재. 진짜 문제를 놓치는 일이 없는 게 헛걸림 줄이는 것보다 먼저야.
```

Claude Code에서는 명령 실행 직전(PreToolUse 훅), 세션 시작(SessionStart 훅), 커밋 직전(pre-commit)이 그 자리다.
