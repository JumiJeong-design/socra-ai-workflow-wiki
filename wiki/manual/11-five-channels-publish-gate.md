# [11] 구축 1. 채널 다섯과 게시 게이트

> 구분: 구축 · 영역: 공통 · 프론트

## 무엇을 세우나

채널마다 역할을 하나씩만 줍니다. 순서는 이렇습니다.

Figma 승인 → 게시 → Git 언어화 → Package 반영 → Storybook 검수 → Worklog 기록

정본(여러 곳이 다르게 말할 때 따르는 원본) 순서는 피그마 > 패키지 > 스토리북(컴포넌트를 상태별로 띄워 보는 화면)입니다. 패키지나 스토리북이 피그마와 다르면 차이를 분류하고 피그마 기준으로 맞춥니다. 피그마에 없는 컴포넌트가 필요하면 패키지나 스토리북을 만들지 않고 피그마 생성·승인 작업으로 분리합니다.

### 채널별 역할

- **Figma.** 시각 기준을 탐색하고 승인하는 곳. 1차 기준은 실제 컴포넌트, 컴포넌트 세트, 변수, 스타일, variant 축입니다. 값은 변수와 스타일로만 씁니다.
- **Git.** 피그마 결정을 FE와 에이전트가 읽을 수 있는 말로 바꾸는 곳. 토큰 계약(컴포넌트를 어떻게 구현할지 적은 약속 문서), 컴포넌트 계약, 규칙, 워크플로 문서. 코드를 저장하는 곳이 아니라 결정을 기록하는 중간 층입니다.
- **Package.** FE가 제품에 쓰는 구현 경계. 승인된 피그마 디자인을 재사용 가능한 소스로 옮기는 단계.
- **Storybook.** 패키지 구현 뒤 디자이너 QA와 상태별 시각 검토를 위한 화면. 여기서 새 컴포넌트 구조를 먼저 만들지 않습니다. Figma를 대체하는 곳이 아닙니다.
- **Worklog와 Wiki.** 진행 기록과 반복 가능한 운영 지식. 여기서 나온 교훈이 Git의 규칙으로 되돌아갑니다. 이 화살표가 닫혀 있어야 기록이 기록으로 끝나지 않습니다.

다섯 중 처음부터 갖추어져 있던 것은 없었습니다. Package만 FE가 준 것이고 나머지 넷은 에이전트와 같이 채웠습니다. Figma 디자인 시스템 파일은 세트와 변수를 에이전트가 올리고 값과 모양은 사람이 정했고, Git의 계약과 규칙은 에이전트가 썼고, Storybook은 패키지에 붙여 세웠고, Worklog는 실험 첫 주부터 같이 썼습니다. 채널을 세운다는 것은 다섯을 미리 갖추는 일이 아니라, 각 채널이 무엇을 맡는지 정하고 빈 채널을 그 역할대로 채워 가는 일입니다.

### 게시 게이트

Figma와 Git 사이에 게시가 있습니다. 디자인 시스템 파일에서 고친 것은 게시해야 제품 파일에 내려갑니다. 변수는 게시하면 수락 없이 자동으로 전파되고, 컴포넌트 구조는 제품 파일에서 수락해야 내려옵니다. 이 단계가 빠지면 에이전트가 제품 파일을 볼 때마다 예전 값을 읽고, 같은 작업을 몇 번을 돌려도 결과가 달라집니다. 게시가 됐는지는 라이브러리 상태값이 아니라 제품 파일 인스턴스가 무엇을 물고 있는지로 잽니다. 게시 대기 목록은 대부분 허수입니다. 14개가 떠 있어도 실제 차이는 둘이었습니다.

### 스토리북의 장점

스토리북은 Figma를 대체하지 않습니다. 그래도 이 루프에서 스토리북이 없으면 안 되는 이유가 넷 있습니다.

1. 디자이너와 FE가 같은 화면을 봅니다. 상태별로 렌더된 것을 같이 보면 「피그마랑 다르다」를 말로 설명할 필요가 없습니다.
2. 계약 수치를 렌더로 검산할 수 있습니다. 헤드리스 브라우저로 재면 폭, 간격, 호버, 전환이 계약대로인지 숫자로 나옵니다. 에이전트가 「됐다」를 재서 말할 수 있는 유일한 자리입니다.
3. 제품에 올라가는 중간 뷰입니다. 스토리가 곧 QA 증거여서, 배포 전에 무엇이 바뀌는지 게시본 두 빌드를 대조하면 됩니다.
4. FE 영토를 건드리지 않고 들어갈 수 있는 자리입니다. 「검수 기준으로만 쓰겠다」로 시작할 수 있었던 건 스토리북이기 때문입니다. [원리 3](#manual-33)에 있습니다.

### 스토리북 화면의 경계

스토리북이 피그마 파일을 페이지 단위로 그대로 옮길 필요는 없습니다. docs 페이지의 배치, 패널, 제목, 설명 영역은 읽기 좋게 자유롭게 짭니다. 다만 렌더된 컴포넌트 안쪽은 피그마와 같아야 합니다. 토큰, 치수, variant, 상태, 글자, 간격, 반경, 그림자, 아이콘 크기가 여기에 듭니다. docs 페이지의 스타일이 컴포넌트 CSS로 새어 들어가 컴포넌트의 기준이 되지 않게 합니다.

### 어디서 확인하나

| 구분 | 무엇 | 어디서 |
| --- | --- | --- |
| 컴포넌트 안 | 타이핑, 포커스, 호버, 눌림, 상태 전환, 로딩, 긴 텍스트, 다국어 | 스토리북 |
| 화면 밖 | 화면 이동, 로그인, 저장, 전역 상태, 성능 | 앱 |

스토리북에서는 아래 축을 스토리로 고정해 둡니다. 그래야 같은 문제를 화면마다 다시 찾지 않습니다. 모든 컴포넌트가 모든 축을 같은 깊이로 가질 필요는 없습니다. 글자 리스크가 큰 컴포넌트는 언어와 긴 내용을, 표면 리스크가 큰 컴포넌트는 테마와 대체 경로를 먼저 둡니다.

| 축 | 확인할 것 |
| --- | --- |
| 테마 | 라이트와 다크 모두에서 토큰과 계층이 맞는가 |
| 화면 폭 | 모바일과 웹 폭에서 조합이 깨지지 않는가 |
| 언어 | 한국어, 영어, 일본어로 문구 길이가 바뀌어도 버티는가 |
| 긴 내용 | 긴 제목, 본문, 리스트가 넘치지 않는가 |
| 빈 상태 | 데이터가 없을 때 구조와 다음 행동이 보이는가 |
| 오류 | 실패가 구별되고 복구 행동이 보이는가 |
| 대체 경로 | 이미지 실패, 기능 제한, 토큰 누락에서 무너지지 않는가 |
| 상호작용·접근성 | 포커스, 키보드, 비활성, 로딩, 접근 가능한 이름이 맞는가 |

## 왜 이 자리가 필요한가

채널이 다섯인 건 각각이 다른 사람의 자리이기 때문입니다. Figma는 디자이너, Package는 FE, Storybook은 둘 다, Worklog는 다음 세션의 나입니다. 역할을 하나씩만 주면 어느 채널에서 무엇이 정해져야 하는지가 분명해지고, 에이전트가 어디서 멈춰야 하는지도 분명해집니다.

게시 게이트는 사고에서 나왔습니다. 게시와 수락을 가르는 규칙은 있었는데 다른 규칙의 하위 항목에 묻혀 열흘간 같은 오판이 반복됐습니다. 루프 그림에 「게시」를 따로 그리게 된 건 그 뒤입니다.

## 만든 뒤 확인할 것

- 지시문 첫 줄에 정본 순서가 있나.
- 제품 파일 인스턴스가 게시본과 같은 것을 물고 있는지 재는 방법이 있나. 없으면 「게시했다」를 믿을 수 없습니다.
- 스토리북에 피그마에 없는 컴포넌트가 있나. 있으면 정본 순서가 이미 깨진 것입니다.
- 「안 바뀐다」의 원인을 넷으로 가를 수 있나. 게시 안 됨, 수락 안 됨, 제품 파일 안에 사본이 여러 벌, 화면에서 직접 덮어쓴 값. 수락했는데도 안 바뀌면 사본 수를 세고 옛 판을 새 판으로 바꿔 끼웁니다. 게시·수락을 사람에게 부탁하지 않습니다. 값이면 직접 넣고, 구조면 「이 게시가 막아 주는 것」을 적습니다.
