AI 워크플로우 가이드

AI 에디터 연결 설정

빠른 시작에서 진입 파일을 만들었다면, 이제 쓰는 도구가 그 파일을 읽게 해야 합니다. 아무리 잘 써 두어도 AI 에디터에 연결되지 않으면 그냥 폴더 안의 파일입니다.

모든 AI 에디터는 프로젝트 루트의 특정 파일을 자동으로 읽습니다. 이 파일 하나가 "AI가 이 프로젝트를 어떻게 이해해야 하는지"를 담는 진입점이 됩니다.

진입점 파일 구조

진입 파일에는 매 세션 필요한 것만 둡니다. 정본 순서, 세션 시작과 끝, 절대 하지 않는 것, 그리고 「이런 상황이면 이 규칙」 색인입니다. 규칙 본문은 따로 두고 색인이 가리키게 합니다.

CLAUDE.md / AGENTS.md / .cursor/rules/design.mdc, 공통 구조
# 이 프로젝트의 에이전트 작업 기준

## 정본 순서
- 피그마 > 패키지 > 스토리북. 다르면 피그마 기준으로 맞춘다.

## 세션 시작과 끝
- 시작: logs/오늘 날짜.md를 먼저 읽는다.
- 끝: 한 일과 남은 일을 같은 파일에 적는다.

## 절대 하지 않는 것
- hardcoded color / spacing (token만 쓴다)
- 접근성 속성 임의 삭제
- 요청 범위 밖의 변경

## 이런 상황이면
피그마 값을 코드로 옮길 때 → docs/rules.md 「토큰 포팅」
화면을 새로 그릴 때     → docs/rules.md 「인스턴스로 그리기」
결과가 「0건」일 때      → docs/rules.md 「범위 다시 적기」

Figma MCP 연결 설정

Figma MCP는 AI 에디터가 Figma 파일을 읽고, 필요한 경우 캔버스에 직접 쓰기 작업까지 수행할 수 있게 하는 연결 통로입니다. 문서 컨텍스트와 달리 Figma 계정 권한, 파일 접근 권한, 사용하는 MCP 방식이 함께 맞아야 안정적으로 동작합니다.

📌

최신 기준: Figma 공식 문서는 대부분의 사용자는 Remote MCP 서버를 쓰는 것을 권장합니다. Desktop MCP 서버는 Figma 데스크탑 앱을 통해 실행되며, 특정 조직/엔터프라이즈 환경에서 필요할 수 있습니다.

공식 문서 참고: Figma MCP Server · Claude Code MCP 설정 · Desktop MCP 설정

구분 Remote MCP Desktop MCP
권장 상황 대부분의 일반 사용, Claude Code/Cursor/Codex 같은 MCP 지원 도구 연결 로컬 데스크탑 앱 기반 연결이 필요한 조직/엔터프라이즈 환경
실행 방식 Figma의 호스팅 엔드포인트에 연결 Figma 데스크탑 앱에서 Dev Mode MCP 서버를 켜고 로컬로 연결
인증 Figma OAuth 승인 중심 데스크탑 앱 + MCP 클라이언트 설정 필요
주의점 승인한 Figma 계정이 접근 가능한 파일만 사용할 수 있음 Figma 데스크탑 앱이 실행 중이고, 대상 파일이 열려 있어야 안정적

연결 전 확인할 것

계정 / 권한
  • OAuth를 승인하는 Figma 계정이 실제 작업 파일에 접근 가능한지 확인
  • 팀 파일을 다룰 경우 Dev 또는 Full seat 권한이 필요한지 확인
  • 공용 계정으로 연결한다면 누가, 어떤 범위까지 접근 가능한지 기록
작업 대상
  • 파일 URL뿐 아니라 작업할 page 또는 node URL까지 준비
  • 여러 페이지가 있는 파일은 AI가 첫 페이지를 기준으로 작업하지 않도록 명시
  • Variables, styles, components를 읽을 수 있는지 첫 테스트에서 확인

기본 연결 흐름

1. AI 도구에서 Figma MCP 연결 추가
Claude Code, Cursor, Codex 등 사용하는 MCP 클라이언트의 공식 설정 화면에서 Figma MCP를 추가합니다.
2. Figma OAuth 승인 계정 확인
승인한 계정이 볼 수 있는 파일만 AI가 접근할 수 있습니다. 팀 파일이면 개인 계정/공용 계정 선택을 먼저 정합니다.
3. Desktop MCP를 쓰는 경우 Dev Mode에서 서버 활성화
Figma 데스크탑 앱에서 대상 파일을 열고 Dev Mode로 전환한 뒤 MCP 서버가 켜져 있는지 확인합니다.
4. IDE/터미널에서 MCP 상태 확인
Claude Code라면 /mcp 같은 서버 상태 화면에서 연결 실패 여부를 확인하고 필요 시 reconnect합니다. Cursor/Codex도 MCP 서버 목록에서 연결 상태를 먼저 봅니다.
5. 첫 테스트는 읽기 작업으로 시작
Figma 링크를 주고 "이 파일의 page 목록, 선택한 frame의 metadata, variables를 읽을 수 있는지 확인해줘"처럼 요청합니다.

첫 연결 테스트 체크리스트

읽기 테스트
  • Figma 파일 URL을 주고 page 목록을 읽을 수 있는지 확인
  • 작업할 frame/node URL을 주고 metadata를 읽을 수 있는지 확인
  • Variables, text styles, component 목록을 읽을 수 있는지 확인
쓰기 테스트
  • 운영 파일이 아닌 테스트 파일에서 작은 text 또는 rectangle을 생성
  • 여러 page가 있는 파일이면 작업 page를 먼저 지정할 수 있는지 확인
  • 실제 디자인 시스템 파일에 쓰기 전에는 반드시 읽기 결과를 먼저 검토
첫 테스트 프롬프트
이 Figma 파일에 접근할 수 있는지 먼저 확인해줘.
1. page 목록을 읽어줘.
2. 이 node URL의 metadata를 요약해줘.
3. 이 파일에서 variables와 text styles를 읽을 수 있는지 확인해줘.
아직 캔버스에는 아무것도 만들지 말고, 읽기 가능 여부만 알려줘.
그대로 적으면 위험한 말
  • "신형 MCP는 항상 Figma 서버에서만 실행된다"
  • "Variable 컬러는 AI가 못 읽는다"
  • "로컬 폰트는 무조건 사용할 수 없다"
정확한 표현
  • Remote MCP와 Desktop MCP는 설정 방식이 다릅니다
  • Variables는 연결 권한과 파일 구조가 맞으면 읽을 수 있습니다
  • 폰트 접근은 Remote/Desktop 방식, Figma 업로드 여부에 따라 달라질 수 있습니다
⚠️

MCP 연결 정보도 운영 문서에 남깁니다. 어떤 계정으로 승인했는지, 어떤 파일을 테스트했는지, 연결 실패 시 어디서 reconnect하는지 기록해두면 공용 계정·공용 파일에서 같은 시행착오를 반복하지 않습니다.

연결한 뒤 작업하다 막히면 Figma MCP 작업 함정 모음을 먼저 봅니다. 같은 증상을 이미 겪고 원인과 피하는 법을 정리해 두었습니다.

너무 일찍 고정하지 않습니다. 처음부터 모든 것을 token과 component로 묶으면 방향이 좁아집니다. 탐색하고, 반복되는 패턴을 보고, 공통 기준을 뽑은 다음에 시스템화합니다.

다음 단계. 피그마 출처가 탐색, 후보를 지나 승인이 되면 그때부터 루프를 돌립니다. 무엇을 갖추고 시작하는지는 AX 매뉴얼 10장 전제에 있습니다. 기준 문서를 먼저 다 써 둘 필요는 없습니다. 디자인 시스템 파일과 지시문은 루프를 돌리면서 같이 자랍니다.

방향 이탈 감지

AI를 쓰면 더 빨리 만들 수 있지만, 더 빨리 엉뚱한 방향으로 갈 수도 있습니다. 리뷰 막판에 품질을 고치는 것과 별개로, 작업 중간에 방향이 틀어지고 있는 신호를 먼저 잡아야 합니다.

신호 의미 대응 액션
피드백이 같은 질문을 맴돕니다 디테일 문제가 아니라 방향 옵션이 부족한 상태 세부 조정을 멈추고 Figma 시안 또는 코드 스파이크 중 가장 빠른 방식으로 2~3개 대안을 새로 만듭니다
뭔가 이상하지만 설명하지 못합니다 시각 품질, 정보 위계, 제품 톤이 섞여 감각적으로 어긋난 상태 Figma AI 에이전트나 감사 체크리스트로 캔버스 전체를 점검합니다
빌드가 초기 제안에서 멀어집니다 구현 과정에서 원래 UX 의도나 비교 기준이 흐려진 상태 원본 시안과 구현 화면을 나란히 두고 차이를 명시합니다
팀이 방향을 고르지 못합니다 선택 기준보다 취향 논의가 앞서는 상태 각 안이 얻는 것과 포기하는 것을 적고, 실제 작동 가능한 대안으로 비교합니다

AI로 모션 시안 만들 때의 프롬프트 흐름

모션은 말로만 설명하면 오해가 큽니다. 레퍼런스 영상, 적용할 화면 캡처, 시간 조건을 함께 주고 한 단계씩 좁혀가는 방식이 더 안정적입니다. 목표는 AI가 최종 모션을 대신 확정하는 것이 아니라, 디자이너가 빠르게 비교하고 개발자에게 설명 가능한 산출물로 정리하는 것입니다.

쓸 만한 상황: Figma 프로토타입만으로 원하는 움직임을 만들기 어렵거나, 모션 디자이너 없이 FE와 “이런 느낌”을 공유해야 할 때. 특히 에러 강조, CTA 피드백, 차트 등장, 입력 누락 안내처럼 짧은 UI 모션에 적합합니다.

1. 레퍼런스 확보: 비슷한 모션을 화면 녹화하거나, 모션 이름을 모르면 AI에게 먼저 이름을 묻습니다
↓
2. 적용 화면 캡처: 실제 적용될 UI를 함께 제공해 위치와 대상 요소를 명확히 합니다
↓
3. 순서를 넘버링: A에서 B로 이동, 100ms 후 강조, 1회만 재생처럼 단계와 시간을 수치로 적습니다
↓
4. 조정 가능한 미리보기 요청: 재생 버튼과 duration/delay 슬라이더를 넣어 디자이너가 감각을 조정하게 합니다
↓
5. CSS 코드와 녹화본 전달: 최종 모션은 CSS 기준 코드, 스크린 녹화, 의도 설명을 함께 개발팀에 넘깁니다

모션 프롬프트에 꼭 넣을 것

항목 넣어야 하는 이유 예시
대상 요소 AI가 화면 전체를 임의로 바꾸는 것을 막기 위해 배송지 정보 타이틀과 라벨만 움직임
상태 변화 모션이 어떤 UX 피드백인지 명확히 하기 위해 미입력 상태에서 CTA 클릭 → 해당 영역 강조
시간값 수정 요청을 감각어가 아닌 수치로 주기 위해 delay 100ms, duration 300ms, 1회 재생
움직임 범위 과한 움직임이나 레이아웃 깨짐을 막기 위해 위로 4px 이동 후 제자리로 돌아옴
조정 UI 디자이너가 직접 속도를 비교하며 결정하기 위해 재생 버튼, duration/delay 슬라이더 포함
최종 전달 형식 FE가 바로 검토할 수 있는 언어로 넘기기 위해 CSS 코드, keyframes, 녹화본, 의도 설명
motion prompt
첨부한 화면에서 미입력 상태의 배송지 영역을 강조하는 모션을 CSS 기반으로 만들어주세요.

순서는 아래와 같습니다.
1. CTA 클릭 후 미입력 영역으로 scroll to
2. 배송지 정보 타이틀과 라벨 UI가 위로 4px 이동
3. 살짝 튕기는 느낌으로 제자리로 돌아옴
4. 모션은 1회만 재생
5. 디자이너가 duration과 delay를 조정할 수 있도록 재생 버튼과 슬라이더를 함께 제공

최종 결과는 CSS 코드로 전달할 수 있게 정리해주세요.

FE 전달 패키지

디자이너가 준비할 것
  • 최종 모션 녹화본 또는 GIF
  • 어떤 상태에서 재생되는지 조건
  • duration, delay, easing 값
  • 움직이는 요소와 움직이면 안 되는 요소
개발자와 확인할 것
  • 실제 코드 스택에 맞는 구현 방식 (CSS, React, emotion 등)
  • 반응형에서 위치가 깨지지 않는지
  • 접근성 설정인 prefers-reduced-motion 처리
  • 재사용 가능한 motion token 또는 utility로 뺄지 여부
⚠️

주의: AI가 만든 미리보기는 종종 원래 UI를 자기 방식으로 다시 그립니다. 모션을 볼 때는 화면 디자인이 아니라 움직임의 타이밍, easing, 방향성만 판단하고, 실제 적용은 기존 컴포넌트와 코드 구조 안에서 다시 검수합니다.

02

가장 중요한 원칙 3가지

원칙 1: AI에게 결과만 요청하지 말고 기준을 제공해야 한다

프롬프트보다 기준이 먼저입니다. 다만 기준 문서를 미리 다 써 둘 필요는 없습니다. 정본 순서와 금지 사항처럼 매번 필요한 것만 진입 파일에 두고, 나머지는 작업하면서 채웁니다.

원칙 2: AI가 반복해서 실수하는 부분은 게이트로 옮긴다

같은 실수를 매번 프롬프트로 설명하면 비효율적입니다. 그렇다고 규칙 문서에 한 줄씩 보태기만 하면, 규칙이 늘어날수록 읽히지 않습니다. 기계로 잡히는 것은 검사와 훅으로 옮기고, 판단이 필요한 것만 규칙으로 적어 진입 파일 색인에서 가리킵니다. 실제로 겪은 일은 규칙이 있는데 같은 실수가 난다에 있습니다.

AI가 primary button을 너무 많이 쓴다
  → 판단이 필요하다: 규칙으로 적고, 색인에 「화면을 새로 그릴 때」로 건다

AI가 임의 색상을 만든다
  → 기계로 잡힌다: hex 직접 입력을 커밋 전 검사로 막는다

AI가 접근성을 빼먹는다
  → 렌더로 잡힌다: 스토리북 접근성 검사에 건다
원칙 3: 문서는 완성물이 아니라 운영하면서 진화하는 기준이다

처음부터 완벽한 문서를 만들 필요는 없습니다. 실제 작업 중 생기는 문제를 기준화하는 흐름이 중요합니다.

AI가 잘못된 결과물 생성
↓
매번 프롬프트로 수정 요청 → 비효율 감지
↓
패턴 파악 → 게이트로 막을 수 있는지 먼저 봅니다
↓
기계로 잡히는 것은 게이트로, 나머지는 색인으로 → 규칙이 늘어도 읽을 양은 그대로
AI가 한 화면에 primary button을 3개 만들었다
  → 규칙: "primary action은 화면당 1개" 추가, 색인에 「화면을 새로 그릴 때」로 건다
  → 그래도 어기면 리뷰 체크 항목으로 올린다

AI가 임의 색상 #3B82F6을 hardcoding했다
  → 커밋 전 검사에 hex 직접 입력 금지를 넣는다
  → 규칙을 안 읽어도 커밋이 막힌다

AI가 생성한 컴포넌트에 focus 상태가 없다
  → 스토리북 상태 스토리와 접근성 검사에 focus를 넣는다
  → 렌더로 확인되니 체크리스트를 늘리지 않아도 된다
AI Workflow 문서는 AI에게 일을 시키기 위한 프롬프트 모음이 아니라, AI가 제품과 디자인 시스템을 이해하고 일관되게 작업하도록 만드는 운영 체계다.

프로덕트 디자이너가 집중해야 할 부분은 코드를 직접 잘 짜는 것이 아니라, AI가 흔들리지 않고 디자인 판단을 보조할 수 있도록 제품 맥락, UX 의도, 컴포넌트 사용 기준, 검토 기준을 구조화하는 것입니다.
