사례: 안 바뀌는 건 게시 때문이 아니었다

구분: 사례 · 기간: 2026-08-18 ~ 09-16 · 관련: 매뉴얼 11장 게시 게이트, 23장 게시와 수락

디자인 시스템 파일에서 마스터를 고쳤는데 제품 파일 화면이 안 바뀌고, AI는 「게시가 필요합니다」라고 하고, 게시 창을 열면 「게시할 게 없습니다」가 뜨는 경우의 사례다. 열여덟 날 동안 AI에게 「게시했어」를 서른 번 넘게 쳤는데, 그중 상당수는 게시할 필요가 없었다.

한눈에

날짜 무슨 일 뒤집힌 것 그래서
8/18 게시했는데 제품 파일이 옛 구조 그대로 게시와 수락은 다른 단계였다 값은 게시로, 구조는 게시와 수락으로 내려온다
8/27 AI가 「게시 대기」라고 적은 19건 전부 이미 내려와 있었다. 0건 게시 여부는 상태 표시 말고 실물로 잰다
8/27 수락했는데도 안 바뀌는 컴포넌트 제품 파일 안에 사본이 두 벌 옛 판을 새 판으로 바꿔 끼운다
9/4 한 세트의 게시가 며칠째 안 나감 그 게시가 막는 건 하나뿐이었다 게시·수락을 사람에게 부탁하지 않는다
9/10 다시 같은 상황 사람이 되묻지 않아도 위 순서로 갔다 처방이 작동
9/16 AI가 원인을 한 사례로 단정해 문서 세 곳에 적음 저녁에 같은 현상이 다른 조건에서 다시 남 가설은 판정 조건과 같이 적는다

원인과 처방

원인 처방
「안 바뀐다」의 원인이 넷인데 AI는 하나로 답했다. 게시 안 됨, 수락 안 됨, 사본이 여러 벌, 화면에서 직접 덮어쓴 값 「게시가 필요합니다」가 나오면 넷 중 어느 경우인지 먼저 가른다
상태 표시는 게시가 남았는지를 말해 주지 않는다 게시 여부는 제품 파일에 실제로 내려왔는지로 판정한다
수락은 사본이 한 벌일 때만 통한다. 여러 벌이면 업데이트 알림도 안 뜬다 수락했는데도 안 바뀌면 사본 수를 세고 옛 판을 새 판으로 바꿔 끼운다
「게시 대기」는 적는 순간부터 낡는다 「게시 대기」를 적을 때는 무엇으로 확인했는지와 날짜를 같은 줄에 적는다
게시 부탁이 습관이 됐다 값이면 직접 넣고, 구조면 「이 게시가 막아 주는 것」을 적는다
원인을 한 사례로 단정했다 가설은 「무엇이 나오면 갈린다」는 판정 조건과 같이 적는다

직접 해 보려면

무엇을 고쳤나 내려오는 길 안 내려올 때 원인
색·문구 같은 값 게시하면 자동 화면에서 직접 타이핑해 덮어쓴 자리
컴포넌트 구조 게시 + 제품 파일에서 수락 제품 파일 안에 사본이 여러 벌
이미 놓인 인스턴스의 값 게시 불필요. 직접 넣는다 
[컴포넌트 이름]이 제품 파일에서 안 바뀌고 있어. 게시하라고 하기 전에 먼저 가르자.
      지금 안 바뀌는 게 ① 변수 값인지 ② 컴포넌트 구조인지 ③ 화면에서 직접 덮어쓴 값인지 ④ 제품 파일 안에 사본이 여러 벌인지 판정해서
      어느 경우인지와 근거를 한 줄씩 적어. 게시가 필요한지는 그다음에 말해.
      
[컴포넌트 이름]의 게시 필요 여부를 라이브러리 상태 표시로 판정하지 마.
      제품 파일 [페이지 이름]에서 그 컴포넌트가 놓인 자리 하나를 잡아, 마스터와 크기·자식·속성이 같은지 대조해 줘.
      같으면 「게시 필요 없음」, 다르면 무엇이 다른지 표로. 「게시 대기」라고 적힌 문서가 있어도 이 방법으로 다시 재.
      
게시했어. 새로 만들거나 바꾼 컴포넌트를 하나씩 제품 파일에서 불러와 보고 새 구조가 잡히는지 「컴포넌트 / 몇 개 중 몇 개」 표로 보여 줘.
      옛 노드 번호로 찾지 말고 컴포넌트 키로 찾아. 게시하면 번호가 바뀌어.
      
제품 파일 [페이지 이름]에 [컴포넌트 이름]의 사본이 몇 벌 있는지 세 줘. 이름이 아니라 컴포넌트 키로 세.
      둘 이상이면 각각 몇 개 자리에서 쓰는지, 어느 게 옛 판인지 표로 가르고, 옛 판을 새 판으로 바꿔 끼우기 전에 대상 목록을 먼저 보여 줘.
      겹쳐 있는 컴포넌트는 안쪽과 바깥을 따로 세.
      
게시가 정말 필요하면 「이 게시가 막아 주는 것」을 한 줄로 적고, 제품 파일에서 실제로 확인한 결과를 같이 올려 줘.
      값 변경이면 게시 부탁하지 말고 이미 놓인 인스턴스에 직접 넣어.

「게시했어」를 하루에 열 번 치고 있다면 첫 프롬프트로 돌아간다.

사례: 규칙이 879줄 있는데 같은 실수가 났다

구분: 사례 · 기간: 2026-08-25 ~ 09-17 · 관련: 매뉴얼 13장 행동 기준, 20장 하네스, 31장 이 방식의 단점

AI가 실수할 때마다 규칙을 한 줄씩 적는데, 규칙이 있는데도 같은 실수가 반복되는 경우의 사례다. 두 달 만에 규칙이 51개 879줄이 됐고, 게시와 수락을 가르는 규칙은 본문이 있었는데도 열흘간 같은 오판이 반복됐다. 「규칙을 왜 안 읽나」가 아니라 「규칙이 왜 안 읽히나」가 문제였다.

한눈에

날짜 무슨 일 뒤집힌 것 그래서
8/25 열흘 반복된 오판의 규칙이 이미 있었다 규칙이 없어서가 아니라 다른 규칙 밑에 묻혀 있었다 규칙 본문 대신 「이럴 때 → 몇 번」 색인을 매 세션 읽히는 파일에
9/2 AI가 같은 실수를 하루 세 번 하고 규칙을 하나 더 썼다 규칙을 늘리면 읽힐 가능성이 줄어든다 커밋 직전 자동 검사로. 그날 작동한 건 전부 자동으로 뜬 것
9/8 지침 문구를 다시 쓰고 있었다 「하지 말라」고 적힌 명령을 아홉 번 실행했다 실행 직전에 막는 훅 셋
9/10~17 훅 헛걸림을 재측 40% → 37.5%, 목표 20%에 못 미침. 훅 파일도 낡아 있었다 넓히지 않고 닫음. 훅도 유지 비용이 있다

색인표는 이런 모양이다. 체크리스트가 아니라 색인이라 절차를 강요하지 않고 판단은 남긴다.

이럴 때 볼 것
뭔가 새로 만들려 할 때 「이미 있나」 규칙
게시·전파를 판정할 때 「게시 ≠ 수락」 규칙
검사 결과가 「0개」로 나올 때 「0건이면 범위를 적는다」 규칙

훅 셋은 이렇다.

언제 무엇을
명령 실행 직전 공유 폴더에서 위험한 git 명령 여덟 가지를 막는다. 격리된 작업 폴더에서는 안 막는다
세션 시작 지금 폴더가 공유 폴더인지, 남은 커밋과 열린 항목이 몇 개인지 첫 화면에 띄운다
커밋 직전 패키지 코드를 바꿨는데 변경 기록이 없으면 막는다

원인과 처방

원인 처방
규칙은 읽어야 작동하고, 읽는 데는 비용이 든다 규칙 본문은 따로 두고, 매 세션 읽히는 파일에는 「이럴 때 → 몇 번」 색인만 둔다
검색은 찾을 단어를 이미 알 때만 걸린다 색인은 증상 이름으로 건다. 규칙마다 처음부터 번호와 「이럴 때 본다」 한 줄을 붙인다
규칙은 알고도 어긴다. 읽기 문제가 아니라 막기 문제다 같은 실수가 두 번 나면 규칙을 더 적지 말고 실행 자리에서 막는다
규칙을 늘리면 읽힐 가능성이 줄어든다 규칙을 늘리자는 제안이 오면 「1번부터 매번 읽다가 놓치는 거 아니야?」를 먼저 묻는다
헛걸리는 게이트는 우회가 습관이 되어 죽는다 게이트는 실제 이력으로 재서 좁힌다. 목표(20% 아래)에 못 미치면 넓히지 않는다
훅도 낡는다 훅 파일이 작업 폴더마다 같은 판인지 가끔 확인한다
발견·결론까지 체크박스로 적으면 열린 항목이 부푼다 체크박스는 「누가 손대면 닫히는 일」에만. 대기 사유에는 「무엇이 어떻게 되면 풀리는지」를 같은 줄에

직접 해 보려면

[규칙 문서 경로]에 있는 규칙마다 번호가 있는지 확인하고, 없으면 붙여 줘.
      규칙마다 「이럴 때 본다」 한 줄을 추가해. 규칙 제목이 아니라 증상으로 적어. 「게시 ≠ 수락」이 아니라 「수락했는데도 안 바뀔 때」처럼.
      바꾼 뒤 「이럴 때 → 번호」 표로 모아서 보여 줘.
      
[규칙 문서 경로]의 본문은 CLAUDE.md에 넣지 말고, 「이럴 때 → 규칙 번호」 표만 만들어서 넣어 줘.
      표 한 줄에 상황 하나, 증상 이름으로. 표가 [기준, 예: 30줄]을 넘으면 어느 줄을 합칠지 먼저 물어.
      
[실수 내용]이 두 번째야. 규칙을 더 적지 말고, 실행 직전이나 커밋 직전에 자동으로 막을 수 있는지 먼저 봐 줘.
      막을 수 있으면 어느 자리(명령 실행 직전·세션 시작·커밋 직전)에 무엇을 만들지 한 줄로 제안하고 내 승인을 받아. 못 막으면 왜 못 막는지 적어.

      헛걸림이 [기준, 예: 20%]를 넘으면 패턴을 좁히고 다시 재. 진짜 문제를 놓치는 일이 없는 게 헛걸림 줄이는 것보다 먼저야.

사례: 「0건」에도 「결함 3곳」에도 되물어야 했다

구분: 사례 · 기간: 2026-08-11 ~ 09-21 · 관련: 매뉴얼 12장 시각 기준, 21장 DS 토큰 정합 검토

피그마 파일을 AI에게 통째로 검사시키고, 결과 표의 숫자를 보고 고칠지 정하는 경우의 사례다. AI 검사는 두 방향으로 틀린다. 있는 것을 「0건」이라고 해서 안 보이게 만들고, 멀쩡한 것을 「결함」이라고 해서 고치게 만든다. 둘 다 겪었고, 둘 다 되물어서 뒤집혔다.

한눈에

날짜 무슨 일 뒤집힌 것 그래서
8/28~29 검사가 화면 78장을 「기획 보드」로 착각해 빼놓았다 「59곳 고쳐야 한다」 → 「왜 고쳐야 하는데?」 → 14곳 빼놓은 수와 기준을 보고에 적는다
9/8 토큰 사용률 0%를 결론으로 두 번 커밋했다 「토큰이 없다」 → 「안 쓴다」 → 이미 다 쓰고 있었다 0이 나오면 다른 방법으로 다시 잰다
9/8 안내 문구 색 3곳을 결함으로 읽어 고쳤다 비활성 상태라 일부러 낮춰 둔 색이었다 결함 목록에 화면 상태를 같이 본다
9/18 검사가 16자리 전부 「없음」을 냈다 AI가 스스로 검사 코드를 의심해 고쳤다 처방이 사람 손 없이 작동
9/21 값을 덮어썼는데 화면이 그대로였다 그 값을 읽는 곳이 없었다 소비처를 먼저 센다

9/8의 0%는 데이터가 아니라 검사 코드가 틀린 것이었다. 피그마에서 값을 읽는 방법이 두 가지인데 두 방법이 같은 항목을 다른 이름으로 부르고, AI는 한 이름으로만 찾아서 3만 건 넘게 못 봤다. 앞서 「고칠 자리 3,132곳」이라고 한 숫자도 이 오류에서 나온 허수였다. 실제로 손으로 값을 넣은 자리는 열한 곳이었다.

원인과 처방

원인 처방
0은 확인할 게 없다. 검사 범위나 코드가 틀려도 똑같이 0이 나온다 0이나 전부 같은 값이 나오면 결과가 아니라 검사 오류로 보고 멈춘다. 표본 셋을 다른 방법으로 다시 읽는다
검사는 값을 재지 의도는 못 잰다 결함 목록에 그 화면의 상태와 투명도를 같은 줄에 적는다. 일부러 둔 것 같으면 「의도 확인」 표로 뺀다
「놓쳤다」와 「고쳐야 한다」는 다르다 「N곳 놓쳤다」에 「왜 고쳐야 하는데」를 묻는다
빼놓은 수를 안 적으면 오판이 남지 않는다 어디를 봤는지, 뺀 것과 기준, 잰 날짜를 보고에 적는다
값이 어긋난 것과 화면이 어긋난 것은 다르다 검사표를 만들기 전에 그 값을 실제로 읽는 곳이 있나부터 센다

직접 해 보려면

피그마 파일에서 [검사할 것]을 전수로 검사해 줘. 조건 셋이 있어.
      1. 결과 표 맨 위에 어디를 봤는지 한 줄로 적어. 페이지 이름, 뺀 것이 있으면 몇 개를 어떤 기준으로 뺐는지, 숨은 요소를 포함했는지.
      2. 검사를 돌리기 전에, 확실히 정상인 자리 셋을 먼저 골라서 그 셋이 「정상」으로 잡히는지 보여 줘. 하나라도 「결함」으로 잡히면 검사 코드가 틀린 거니까 거기서 멈춰.
      3. 결과가 전부 0이거나 전부 같은 값이면 결과가 아니라 검사 오류로 보고 멈춰.
      
방금 검사 결과가 0(또는 0%)으로 나왔어. 결론을 쓰기 전에 검사식부터 의심해.
      확실히 [정상 상태]인 자리 셋을 골라서, 지금 쓴 방법과 다른 방법(예: 다른 API, 화면을 직접 열어 읽기)으로 같은 값을 다시 읽어 줘.

      옛 세대를 무는 자리는 목록만 보여 주고, 내 승인 전에는 바꾸지 마.
      
[램프 이름]의 값을 바꾸려고 해. 바꾸기 전에 그 램프 번호를 직접 무는 자리(semantic을 거치지 않는 것)를 피그마와 코드 양쪽에서 세 줘.
      직접 문 자리는 램프가 움직여도 안 따라오니까, 그 목록을 먼저 보여 주고 어느 것을 semantic으로 옮길지 정한 뒤 값을 바꿔.
      
어긋났다고 보고할 자리마다 그 자리가 값을 어디서 받는지(램프 직접 / semantic 경유 / 손으로 박은 값) 같은 줄에 적어.
      semantic을 거치는 자리는 값이 따라왔을 수 있으니 마스터를 열어 실제 값을 확인한 뒤에 어긋났다고 적어.

사례: 일본어 문구의 정본이 세 군데였다

구분: 사례 · 기간: 2026-09-02 ~ 09-23 · 관련: 매뉴얼 26장 판단을 올릴 때, 33장 중간안

출시 언어가 한국어가 아닌 제품에서, 피그마 화면 문구가 맞는지 AI에게 검수시키는 경우의 사례다. 일본 출시가 확정이고 한국어는 개발 편의였다. JP 문구를 검수하려고 화면을 열었더니 같은 문구가 화면 텍스트, 피그마 변수, 기획 시트 세 군데에서 서로 달랐다. 어느 것이 맞는지 디자인이 정할 수 없는데, 화면은 그중 하나를 이미 보여 주고 있었다.

날짜 무슨 일 뒤집힌 것 그래서

원인과 처방

원인 처방
피그마가 돌려주는 텍스트는 모드 해석 전 값이다. 언어 모드를 걸지 않으면 기본 언어를 잰다 출시 언어가 기본 언어가 아니면 감사 전에 페이지에 언어 모드를 걸고 화면으로 잰다
언어 컬렉션이 여러 벌 살아 있으면 어느 것을 갈아도 화면 일부만 바뀐다 디자인 문구 변수는 디자인 시스템에만. 제품 파일에 로컬 문구 컬렉션을 만들지 않는다
문구의 정본이 디자인 밖에 있는데 화면은 그중 하나를 이미 보여 준다 디자인은 다르다는 사실과 수치만 보여 준다. 어느 것이 정본인지는 기획이 정한다
「기획서에 없다」에서 멈추면 항목이 안 닫힌다 진짜 없는 것은 「무엇이 되면 닫히나」를 적고, 다른 곳에 이미 있는 것은 찾아서 닫는다. 후자가 더 많았다
AI가 문구 자체를 검사 대상으로 삼는다 정본이 정해진 뒤 디자인이 볼 것은 하나다. 화면에 들어갔을 때 깨지지 않는가
