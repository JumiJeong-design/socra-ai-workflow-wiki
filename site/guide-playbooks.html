Screen Design Playbook

When To Use

Socra 제품의 새 화면이나 주요 화면 개편을 AI와 함께 설계할 때 사용한다.

Principle

화면 설계는 Figma에서 자유롭게 탐색하되, approved screen이 되기 전까지 Prism(소크라의 디자인 시스템 패키지) contract, code, Storybook의 구현 계약으로 보지 않는다.

Figma Screen States

Status Meaning Action
exploration 구조, 톤, layout을 자유롭게 실험 worklog/context only
candidate 제품 방향으로 가능성 있는 안 compare and review
approved screen 구현 기준으로 합의된 화면 Prism contract / Storybook 기준 확인
archived 버린 안 또는 과거 실험 keep only as rationale

Page-First Validation

신규 컴포넌트가 여러 개 필요한 화면은 컴포넌트를 모두 구현하기 전에 page shell story로 먼저 검증한다.

  1. 승인된 기존 컴포넌트만 사용해 화면의 큰 구조를 만든다.
  2. 아직 구현 전인 컴포넌트 자리는 placeholder로 명시한다.
  3. mobile/web, light/dark, locale, long content 같은 큰 축에서 화면이 성립하는지 확인한다.
  4. 새 컴포넌트가 준비되면 placeholder를 실제 컴포넌트로 교체한다.
  5. placeholder와 page shell 스타일은 구현 계약이 아니며 컴포넌트 contract로 승격하지 않는다.

Steps

  1. 화면의 핵심 사용자 목적을 한 문장으로 적는다.
  2. Figma screen status를 exploration, candidate, approved screen, archived 중 하나로 표시한다.
  3. Exploration 단계에서는 빠른 조합과 시각 실험을 우선하고 Prism contract로 옮기지 않는다.
  4. Candidate 단계에서는 AI design review로 정보 구조, 상태, 접근성, 컴포넌트 gap을 비교한다.
  5. Approved screen이 되면 필요한 기존 design system component를 확정한다.
  6. 반복 가능한 gap이 실제 구현 계약으로 이어지면 Prism의 최신 source-of-truth 문서에서 spec/contract 반영 범위를 확인한다.
  7. 구현 대상이면 Prism의 기준에 따라 Storybook 또는 product preview에서 구현 상태를 검증한다.
  8. 결정된 반복 패턴은 이 workflow wiki의 guide/playbook으로 승격할지 판단한다.

Done Criteria

  • 화면의 Figma status가 명확하다.
  • Exploration/Candidate 화면이 실수로 구현 기준이 되지 않았다.
  • Approved screen은 디자인 시스템 컴포넌트 기반으로 설명된다.
  • 새 컴포넌트 후보와 one-off UI가 구분된다.
  • 구현 전 page-first 검증이 필요한 경우 shell story와 placeholder 범위가 구분되어 있다.
  • open question과 designer judgment가 분리되어 있다.
  • 구현된 화면 또는 컴포넌트는 Storybook/product preview 검증 경로가 있다.

대량 작업·재발 방지 플레이북

언제 사용하나

수십~수백 건을 한 번에 만지는 작업(전수 감사, 일괄 스왑·치환, 대량 write)을 시작할 때, 그리고 같은 실수가 반복되는 패턴을 끊고 싶을 때 사용한다. 2026년 7~8월 디자인 시스템 게시·정합 운영에서 반복 검증된 규칙만 남긴다.

감사 → 승인 → 실행

공유 디자인 파일에 대한 write는 되돌리기가 비싸다. 순서를 분리한다.

  1. read-only 감사: 대상을 전수로 세고 목록을 만든다. 이 단계에서 "지시받은 대상 일부가 이미 아무도 안 쓰는 고아"라는 사실이 먼저 드러난다.
  2. 변경안 보고: 파괴적 작업(삭제, variant 제거) 전에는 역참조를 전수로 세어 목록을 사람에게 먼저 보인다. 셌으니 지우는 것이고 안 셌으면 깨진다.
  3. 승인 후 write: 승인된 범위만 실행한다.

되돌리기 쉬운 일은 반대로 묻지 않고 그냥 한다. 확인 요청이 잦으면 진행 자체가 멈춘다.

파일럿 1건 → 배치

같은 유형 N건을 한 번에 돌리면 같은 오류를 N배로 만난다.

  1. 첫 1건으로 헬퍼·레이아웃 계산을 검증한다 (스크린샷/실측).
  2. 나머지를 같은 틀로 배치 실행한다.
  3. 전후 대조로 마감한다.

검증 명령이 실제 게이트와 같은지 확인한다. 로컬에서 typecheck·test만 돌리고 "통과"라고 보고했는데 CI가 도는 통합 명령에서 반나절 깨져 있던 일이 반복됐다.

전수 감사의 숫자는 정의가 먼저다

같은 대상이 집계 단위에 따라 846개 → 44개 → 16개로 줄어든 적이 있다. 아무것도 안 고쳤는데 계획이 계속 틀렸던 셈이다.

  • 감사 보고에는 집계 단위(톱레벨/중첩 포함), 스캔 범위(전 페이지, hidden 포함 여부, 타입 커버리지), 제외군을 항상 명시한다. "전수"라고 말하려면 범위를 함께 적는다.
  • 개수보다 분포의 모양을 본다. 값이 축별로 깔끔하게 갈리면 인스턴스 오버라이드가 아니라 상위 마스터 내부값이 뿌리다. 마스터 24개를 고쳐 인스턴스 236개가 자동 정합된 사례가 있다.

재발 방지 규칙

자동화는 조용히 썩는다

스킬·프롬프트 절차는 참조 대상이 바뀌어도 문법 오류 없이 결과만 틀리게 나온다. 고친 스킬은 반드시 한 번 실행해야 검증된 것이다. "고쳤다"와 "돈다"는 다르다. 오탐(없는 문제 보고)은 즉시 걸리지만 안 해도 될 일을 계속 하는 쪽은 아무도 걸러내지 않아 훨씬 오래 남는다.

낡은 문서는 사람의 결정을 뒤집는다

에이전트가 몇 주 전 문서에 남은 "배포하지 않는다" 한 줄을 근거로, 이미 합의된 배포를 스스로 취소한 일이 있다. 방침을 폐기하면 그 문장을 같은 턴에 지운다. 결정 문서에는 무엇을 폐기했는지 함께 적는다. 세션이 갈리면 앞 결정을 안 읽어 서로 배타적인 두 결정이 각각 승인된 채 공존한다.

목록을 믿지 말고 실물을 조회한다

미결 목록의 항목이 이미 확정돼 있고 "확정"으로 적힌 항목이 실은 자체 승인이었던 일이 양방향으로 반복됐다. 착수 전 재실측을 0단계로 둔다. 브리핑의 파일·줄번호·노드가 이미 사라졌거나 이름이 바뀐 사례가 잦다. 잔무 목록은 순서가 아니라 후보다. 집기 전에 "지금 이게 뭘 사주나"를 먼저 답한다.

"A 때문에 대기"로 적힌 항목은 재측 전까지 열린 항목이 아니라 낡은 항목으로 본다. 2026년 9월 한 달 동안 대기 사유를 다시 재니 이미 풀려 있던 일이 여섯 번 있었다. 기획 회신이 이미 왔거나, 권한이 이미 열렸거나, 선행 PR이 이미 머지돼 있었다. 대기 사유에는 무엇이 오면 풀리는지와 마지막으로 잰 날짜를 같이 적는다.

근거 없는 요소를 만들지 않는다

스펙에 없는 A를 넣으면 A를 설명할 B가 필요해지고 B가 A를 정당화하는 순환이 생긴다. 새 요소는 스펙 원문에 근거가 있는지 확인하고 없으면 "확정"이 아니라 "디자인 제안"으로 표기한다. 철회는 아래로 번진다. 결정을 되돌릴 땐 그 결정을 참조하던 주석·표·변수·후속 항목을 같이 훑는다.

증상을 원인으로 옮겨 적지 않는다

"여백 8px 어긋남" 두 건 중 하나는 패딩, 하나는 컨테이너 폭 문제였다. 판정 전에 실측한다. 헤드리스 캡처·계측 한 번이 추측 세 번보다 빠르고 정확하다. 위반처럼 보이면 소속 프레임/맥락부터 확인한다. 참고용·아카이브 영역의 더미가 위반으로 집계되는 일이 반복됐다.

규칙을 늘리지 말고 색인을 둔다

규칙 문서가 수백 줄이 되면 통독은 낭비이고 통독해도 작업 순간에는 떠오르지 않는다. 워크로그 61일·함정 503건을 전수로 훑어 규칙에 없는데 반복되는 것만 골랐더니, 가장 많이 반복된 규칙은 이미 있었다. 제목과 무관한 규칙의 하위 불릿에 묻혀 있어서 훑어도 안 나왔을 뿐이다. 새 규칙은 제목이 내용을 말하는 자리에 두고 세션마다 자동 주입되는 진입 파일에는 "상황 → 규칙 번호" 색인만 둔다. 체크리스트가 아니라 색인이다. 절차를 강요하지 않고 판단은 남긴다.

완료 기준 플레이북: 1차 / 공유 가능 / 픽스

언제 사용하나

에이전트가 "완료"라고 보고했는데 디자이너 눈에는 남은 일이 보일 때, 그리고 팀에 화면 일정을 말해야 할 때 사용한다. 2026년 8월에 규칙으로 정했고 이후 에이전트 보고 형식으로 쓰고 있다.

왜 완료를 나누나

에이전트의 "완료"와 디자이너의 "완료"가 다르다. 에이전트는 기획과 구조가 그려지면 끝났다고 보고 디자이너 기준으로는 시각 품질과 UX 검토가 남아 있다. 이 간극 때문에 남은 일이 어디에도 기록되지 않은 채 사람 머릿속에만 쌓인다.

일이 도착하는 모양도 바뀌었다. 기획→디자인→개발→QA로 한 번에 하나씩 오던 구조에서, 화면 설계·컴포넌트·문서·QA 준비가 에이전트 완료 시점에 동시에 도착하는 구조가 됐다. 검수 1명 앞에 큐가 생기고 열어보기 전에는 10분짜리 확인인지 2시간짜리 재작업인지 모른다. "이 화면 2.5일" 같은 점 추정은 순차 전제에서만 성립한다.

3단계

단계 뜻 누가 선언 공유
1차 기획·구조가 그려짐 에이전트 공유하지 않음
공유 가능 구조·방향이 섬. 디테일은 미픽스 에이전트 자가 검사 → 디자이너 확인 팀 공유 OK
픽스 품질·UX 검토 끝 디자이너만 변경 시 공지

기존 Figma 화면 상태와 같은 사다리다. 공유 가능 ≈ candidate, 픽스 ≈ approved screen.

에이전트 보고 규칙

  • "완료"를 단독으로 쓰지 않는다. 항상 단계명으로 보고한다.
  • 1차 완료. 남은 것: 시각 품질, UX 흐름처럼 남은 단계를 문장으로 남긴다.
  • 공유 가능은 아래 기준을 자가 검사하고 결과를 보고에 붙였을 때만 선언한다.
  • 픽스는 에이전트가 선언할 수 없다. 준비만 한다.

공유 가능 기준

하나라도 빠지면 공유 가능으로 부르지 않는다.

  1. 목적 한 문장: 이 화면이 해결하는 사용자 목적
  2. 핵심 흐름·분기: IA와 사용자 분기가 정의됨
  3. DS 준수: 승인된 컴포넌트·인스턴스만 사용. 손코딩 0
  4. 핵심 상태: 그 화면에 필요한 상태가 있음 (empty/loading/error 전체 강제는 아님)
  5. 출처 근거: Figma node id·variables 또는 패키지 계약. 없으면 pending으로 두고 추측하지 않는다
  6. 미결 질문 분리: 디자이너 판단이 필요한 항목이 목록으로 뽑혀 있음
  7. 공유 라벨: 구조·플로우 픽스 / 비주얼·디테일 미픽스처럼 무엇이 픽스인지 명시

문구는 lorem만 아니면 된다. 확정 문구는 픽스 몫이다.

픽스 기준

디자이너 판단이다.

  1. UX 흐름: 사용자가 주요 행동을 바로 찾는가
  2. 시각 품질: 위계·밸런스·브랜드 톤
  3. 토큰 준수: spacing·typography·color 임의값 0
  4. QA 축: 전 축이 아니라 그 컴포넌트의 리스크 우선 축만. 축 정의는 AX 매뉴얼 11장에 있다
  5. 실제 도는 표면에서 확인: 컴포넌트 안은 Storybook, 화면 밖은 앱
  6. 승인 기록: 승인 대기와 승인 완료를 구분해 기록

일정은 두 날짜로 말한다

  • 공유 가능일은 예측 가능하니 팀에 약속한다. 이 날 FE 착수와 리뷰가 시작되고 디자이너 품질 검토는 그 뒤로 병렬 진행한다.
  • 픽스일은 AI 품질 편차와 진행 중 발견되는 범위 때문에 구간으로만 말하고 진행하며 갱신한다.
  • 날짜가 박힌 일은 처음부터 병렬 밖으로 빼서 순차로 처리한다.
  • 공유할 때 라벨을 빼면 미픽스 디테일에 피드백이 쏟아져 부하가 오히려 늘어난다.
