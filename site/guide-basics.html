3개 Phase 플랜
⚡

지금 당장 시작하려면

기준 문서를 먼저 다 써 둘 필요는 없다. 자리 셋과 결정 하나만 있으면 첫 작업을 시작할 수 있다. 안은 에이전트와 같이 일하면서 채운다.

1. 진입 파일 만들기
레포 루트에 에이전트가 세션마다 읽는 파일(AGENTS.md 또는 CLAUDE.md)을 둔다. 이 파일이 없으면 대화가 끝날 때 규칙도 같이 사라진다.
2분
2. 정본 순서 한 줄 적기
피그마, 코드, 스토리북 중 어느 쪽이 기준이고 어느 쪽이 따라가는지 진입 파일에 적는다. 정하지 않으면 에이전트가 매번 다르게 판단한다.
3분
3. 워크로그 자리 만들기
날짜별 파일 하나를 둘 폴더를 정하고, 진입 파일에 「시작할 때 오늘 것을 읽고 끝날 때 적는다」를 적는다. 세션 사이를 이어 주는 장치다.
5분
4. 화면 하나 맡겨 보기
진입 파일이 읽히는지 확인하고 작업 하나를 맡긴다. 틀린 것은 규칙으로 적되, 규칙이 늘어나면 통째로 읽히지 않으니 색인과 훅으로 옮긴다.

현장 이슈와 AI 역할 구분

AI Workflow를 구축하기 전에, 현재 디자인 업무에서 실제로 비효율이 있는 지점을 먼저 파악해야 한다. 그 중에서 AI가 해결할 수 있는 것과 사람이 직접 판단해야 하는 것을 구분하는 것이 출발점이다.

기존 업무에서 부담이 큰 지점

화면화 / 제작
  • 기획서를 화면으로 다시 해석해야 함. 기획 내용이 바로 개발 가능한 화면 형태가 아님
  • 요구사항 변경으로 반복 수정이 많음. 특히 초기 제품, 신규 기능
  • 디자이너의 역할 범위가 과도하게 넓어짐: 화면 기획부터 QA까지 연속 담당
전달 / 검수
  • 개발 핸드오프가 수작업에 가까움: 컴포넌트, 상태값, 예외 케이스 별도 정리 필요
  • 구현 이후 디자인 QA 부담이 큼: 간격, 정렬, 반응형, 브랜드 톤 재확인
  • 핵심 판단보다 화면화/전달/검수에 시간이 더 많이 쓰임

AI 도입 시 새로 생기는 이슈

  • AI 결과물의 품질 편차가 큼: 브랜드 톤, UX 일관성, 디테일 품질이 흔들릴 수 있음
  • AI 활용 기준이 없음: 어떤 화면을 맡겨도 되는지, 어떤 부분은 직접 판단해야 하는지 기준 부재
  • 히스토리 관리가 어려워짐: Figma, 코드, 문서가 분산될 경우 최신 기준과 결정 이유 추적 어려움

AI vs 인간: 잘하는 일과 한계

구분 잘하는 일 부담이 크거나 한계인 일
AI 구조화, 반복 생성, 변형안 제작, 체크리스트화, 누락 점검, 문서화 자동화 제품 맥락 이해, 브랜드 감도 판단, 복잡한 UX 의사결정, 비즈니스/정책 판단, 최종 책임
인간 문제 정의, 제품 방향 결정, 브랜드 감도 판단, UX 맥락 해석, 우선순위 결정, 최종 품질 판단 빈 화면에서 초안 만들기, 반복 UI 대량 제작, 모든 상태값 기억, 핸드오프 항목 정리, QA 반복 검수, 변경 이력 정리

AI로 해결 가능한 업무

화면 초안
기획서 기반 1차 구조화
기획서를 AI에 입력해 화면 목적, 주요 섹션, 상태값, 예외 케이스 초안을 생성. 디자이너는 UX 흐름과 브랜드 기준으로 검토/수정.
반복 UI
패턴화된 UI 빠른 생성
카드, 리스트, 폼, 빈 상태, 에러/로딩 상태처럼 구조가 반복되는 UI. 컴포넌트 규칙을 프롬프트에 포함해 디자인 시스템 안에서 생성.
핸드오프
체크리스트 자동화
화면 기획서나 시안을 AI에 입력해 컴포넌트, 상태값, 반응형, 문구, API 필요 여부 등 개발 전달 항목을 자동 추출.
QA
사전 점검 보조
구현 화면 기준으로 누락된 상태, 불명확한 문구, 반응형 이슈, 디자인 시스템 위반 가능성을 AI가 1차 점검. 최종 QA는 디자이너 직접 진행.
브랜드
결과물 편차 감소
브랜드 톤앤매너, 문구 스타일, 피해야 할 느낌을 가이드로 정리해 프롬프트에 포함. AI 결과물의 브랜드 편차를 줄이고, 맞지 않는 경우 재생성.
문서화
재사용 가능한 프로세스
잘 작동한 프롬프트와 실패한 프롬프트를 기록해 팀 문서로 정리. 반복 가능한 업무 방식으로 체계화.

AI로 해결이 어려운 업무

⚠️

제품 방향성, 핵심 UX 판단, 우선순위 결정은 AI가 대신할 수 없다.
B2C 제품에서 중요한 브랜드 첫인상, 감정 설계, 신뢰감 형성은 디자이너가 직접 판단해야 한다.
복잡한 사용자 맥락, 정책, 비즈니스 조건이 얽힌 화면은 AI 초안만으로 결정하기 어렵고, 조직 전체의 협업 방식, 의사결정 구조는 AI 도입만으로 해결되지 않는다.

AI 중심으로 전환할 때 실제로 달라지는 것

기존 Figma 중심
기획 → Figma 디자인
개발 전달 (핸드오프)
QA → 수정 요청

시각적 명세 명확, 역할 구분 안정, 히스토리 관리 쉬움

AI 중심
프롬프트 → AI 생성
디자이너 직접 수정
코드 기반 즉시 반영

속도 빠름, 반복 생산 쉬움, 역할 경계 흐려짐, 관리 체계 아직 불안정

장점 ①
구현 속도
반복 UI, CRUD, 어드민, 공통 화면은 AI 기반 생성이 훨씬 빠름. 디자이너가 직접 수정하고 즉시 확인 가능.
장점 ②
커뮤니케이션 비용 감소
디자이너가 직접 컴포넌트 수정 → 즉시 반영. 수정 요청 → 대기 → 재확인 루프가 줄어들기 시작.
장점 ③
공통 언어
디자이너와 개발자가 같은 컴포넌트 구조와 네이밍을 쓰면 아이데이션과 스펙 논의 속도가 빨라짐.

아직 해결 안 된 문제들

히스토리 관리
  • 어떤 수정본이 최신인지 추적 어려움
  • AI가 결과를 계속 뒤집어도 결정 이력이 안 남음
  • Figma처럼 시각적 비교가 안 됨. Git + 문서 조합 필요
협업 충돌
  • 디자이너 수정 → 개발자 수정 → AI 재생성 → 코드 충돌 반복
  • SOT(Source of Truth: 팀의 최신 기준이 되는 단일 출처) 가 어느 쪽인지 불명확하면 구조 붕괴
  • 피그마와 코드 라이브러리 싱크 유지가 어려움
Ownership 감각 변화
  • "AI가 추천해서 만든 것"이 반복되면 설계 주도권이 흐려짐
  • 브랜드 감각, 인터랙션 디테일은 사람이 강하게 개입해야 유지됨
일정 예측 어려움
  • 실험적 작업은 일정 산정이 어려움: 리스크 허용 범위를 팀이 사전 합의해야 함
  • 프롬프팅 비용이 예상보다 클 수 있음. 맥락이 많을수록 사람이 더 빠른 경우도 있음
💡

현재 가장 현실적인 접근은 혼합형이다. Figma는 탐색·확정·히스토리 도구로 유지하고, AI + 코드는 반복 UI 제작·수정·검증에 집중하는 방식. 완벽한 자동화보다 빠른 반복과 공통 언어 기반 협업 구조를 만드는 것이 핵심이다.

최종 Goal: 디자이너에게 집중되어 있던 화면 구체화, 개발 핸드오프, QA 부담을 줄이고: AI를 활용할 수 있는 업무와 디자이너가 반드시 직접 판단해야 하는 업무를 구분하는 기준을 만든다. B2C 제품의 브랜드 품질과 핵심 경험 완성도는 유지하면서, 반복 작업과 수정 작업의 속도를 높인다.

제품 단계별 AI 활용 전략

AI 디자인 프로세스는 "Figma를 대체하느냐"의 문제가 아니다. 제품 단계와 성격에 따라 어디까지 AI에 맡길지를 정하는 문제다.

Figma의 역할은 팀 구조와 프로세스에 따라 다르다. 이해관계자 합의가 중요한 팀은 Figma를 최종 명세 문서로 계속 유지하고, 빠른 구현이 중심인 팀은 탐색·합의용으로만 쓰기도 한다. 중요한 건 Figma냐 AI냐가 아니라, 팀이 합의한 방식으로 일관되게 운영하는 것이다.

📌

아래 흐름은 하나의 예시다. 팀의 디자이너/개발자 구성, 이해관계자 환경, 제품 성격에 따라 Figma의 비중은 달라질 수 있다.

초기 방향/플로우: Figma (탐색, 이해관계자 합의) 또는 AI 텍스트 스케치
반복 화면/구현: AI + 코드 (생산, 수정)
디테일 수정/QA: 실제 프론트 (검증, 품질)
히스토리: Git (결정 기록, 이력 관리)

AI 중심 프로세스가 더 나은 경우

AI 중심이 유리한 조건
  • 내부 툴, SaaS, 어드민, 반복 UI가 많은 서비스
  • 빠르게 만들고 실제 화면에서 바로 고치는 조직
  • 디자이너가 CSS/프론트 구조를 어느 정도 이해하는 팀
  • Git/문서/QA 룰을 잡을 수 있는 팀
  • 완벽한 시안보다 빠른 검증이 중요한 단계
AI 중심이 오히려 혼란을 키우는 조건
  • 브랜드 감도나 비주얼 완성도가 중요한 B2C
  • 이해관계자가 많아서 시각적 합의가 중요한 조직
  • 디자이너와 개발자 역할이 엄격히 나뉜 팀
  • Git, 코드 리뷰, QA 체계가 약한 팀
  • 디자이너가 실제 구현물을 만질 준비가 안 된 팀

제품 성장 단계별 추천 접근

0 → 1
빠른 검증: 속도가 중요하지만 핵심 경험 품질은 지킨다

AI는 초안 생성, 화면 구조화, 반복 UI 제작에 강하다. 단 B2C라면 랜딩·온보딩·결제 같은 첫인상 구간은 디자이너가 브랜드 감각을 직접 잡아야 한다.

PM/PO: 문제와 가설 정의
↓
Designer: 브랜드 방향, 핵심 UX, 첫인상 설계
↓
AI: 화면 초안/반복 UI 생성
↓
FE: 실제 구현 구조화  |  BE, 핵심 데이터/API 연결
↓
Designer + PM/PO: 실제 화면 QA → User test → 반응 확인

0→1 후반에서는 AI로 빠르게 만들되, 디자인 시스템과 브랜드 가드레일은 처음부터 적용한다.

1 → 10
시스템 기반 운영: AI 자유 생성이 아닌 통제 가능한 생성

화면과 기능이 늘면서 스타일이 흔들리고, 컴포넌트가 제각각이 되고, UX 일관성이 깨지기 쉽다. 이때부터는 디자인 시스템이 AI 생성의 가드레일이 된다.

이 단계에서 필요한 것
  • 디자인 시스템 + 컴포넌트 룰
  • 디자인 토큰 + 상태값 정의
  • 히스토리 관리
  • AI 생성 가드레일 (진입 파일의 규칙 색인과 훅)
추천 흐름
Figma: 브랜드/시스템 기준 관리
AI: 시스템 안에서만 화면 생성
Codebase: 실제 구현과 운영 기준
Git/문서: 변경 이력과 결정 기록
10 → 100
안정성 우선: AI는 creator에서 accelerator로

제품이 커지면 속도보다 안정성이 중요해진다. 디자인 문제가 아니라 운영·조직·거버넌스 문제가 된다.

이 단계의 주요 이슈
접근성, 다크모드, 다국어, 예외 케이스, 권한/상태별 화면, 의사결정 기록, 코드 품질
AI의 역할 변화
이전
AI = creator (메인 제작자)
이후
AI = accelerator (보조/자동화)

QA 보조, 리팩토링, 마이그레이션, variation 생성, 문서화 자동화에 더 적합하다.

💡

디자이너는 단순히 화면을 그리는 사람이 아니라, AI가 만든 결과물이 제품답게 보이고 작동하도록 품질을 관리하는 사람에 가까워진다.

AI 시대의 디자인 프로세스는 "더 빨리 만드는 방식"이 아니라, 제품 단계에 맞게 속도 · 브랜드 · 일관성 · 안정성의 균형을 다시 설계하는 방식이다.
