탐색 단계에서 기준 찾기 루프 전

에이전트와 같이 피그마, 패키지, 스토리북을 맞추는 루프는 방향이 정해진 뒤에 돌린다. 탐색 중인 시안은 계약도 코드도 바꾸지 않고 기록에만 남긴다. 이 단계의 목적은 완성된 결과물이 아니라 다음 단계로 넘길 기준을 발견하는 것이다.

① 레퍼런스 수집: Dribbble, Mobbin, 경쟁 서비스, 무드보드 등에서 방향성 탐색
↓
② 서비스 탐색 / 분석: 유사 서비스의 화면 구조, 인터랙션 패턴, 정보 위계 파악
↓
③ 방향성 좁히기: 키워드, 톤앤매너, 비주얼 무드를 언어로 정의하기 시작
↓
④ 반복 패턴 발견: 어떤 UI가 반복되는지, 어떤 컴포넌트가 공통인지 인식
↓
⑤ 기준 추출: 발견한 패턴에서 token, component, UX 원칙 후보를 뽑는다

프로덕트 관점에서 초기 방향 잡기

탐색은 예쁜 화면 찾기가 아니다. 제품이 푸는 문제, 사용자 행동 흐름, 핵심 CTA 구조를 같이 고민한다. 아래 질문이 방향을 잡아 준다.

Product
제품 맥락 정의
이 제품이 해결하는 핵심 문제는 무엇인가? 사용자가 처음 만나는 화면에서 무엇을 이해해야 하는가? 제품의 톤과 신뢰감은 어디서 오는가?
Flow
핵심 사용자 플로우
사용자의 가장 중요한 행동 흐름은 무엇인가? 진입 → 탐색 → 실행 → 피드백의 각 단계에서 무엇이 필요한가?
Priority
정보 위계와 CTA
한 화면에서 사용자가 가장 먼저 봐야 하는 것은 무엇인가? primary action은 무엇이고, 보조 행동은 어디에 위치하는가?
Pattern
반복되는 UI 패턴
어떤 UI 구조가 여러 화면에 반복되는가? 카드, 리스트, 입력 폼, 피드백 메시지, 이 패턴들이 컴포넌트 후보가 된다.
⚠️

너무 일찍 고정하지 않는다. 처음부터 모든 것을 token과 component로 묶으면 방향이 좁아진다. 탐색하고, 반복되는 패턴을 보고, 공통 기준을 뽑은 다음에 시스템화한다.

→

다음 단계. 피그마 출처가 탐색, 후보를 지나 승인이 되면 그때부터 루프를 돌린다. 무엇을 갖추고 시작하는지는 AX 매뉴얼 10장 전제에 있다. 기준 문서를 먼저 다 써 둘 필요는 없다. 디자인 시스템 파일과 지시문은 루프를 돌리면서 같이 자란다.
