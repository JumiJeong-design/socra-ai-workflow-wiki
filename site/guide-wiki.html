실무 가이드

디자이너를 위한 개발 협업 용어 가이드

디자인 시스템이나 제품 UI를 AI/개발자와 함께 다루다 보면 PR, CI, Storybook, Token 같은 개발 용어를 자주 만나게 됩니다. 이 문서는 디자이너가 작업 흐름을 이해하고 변경사항을 안전하게 확인하기 위해 필요한 기본 용어를 정리합니다.

이 문서는 제품/package 계약 문서가 아닙니다. 실제 Prism(소크라의 디자인 시스템 패키지) 컴포넌트, 토큰, Storybook, 배포 기준의 source of truth는 Prism입니다.

이 위키에서 쓰는 말

매뉴얼과 사례에 자주 나오는 말입니다. 개발 용어는 아래에 따로 있습니다.

말 뜻 자세히
정본 여러 곳이 다르게 말할 때 따르는 원본. 이 위키에서는 피그마 > 패키지 > 스토리북 순서입니다 매뉴얼 11
계약 컴포넌트를 어떻게 구현할지 적은 약속 문서. 받는 값, 상태, 쓰는 토큰이 들어갑니다 아래 Contract
게시 게이트 디자인 시스템 변경이 제품 화면에 닿기 전에 사람이 확인하는 단계 매뉴얼 11
진입 파일 에이전트가 세션마다 먼저 읽는 파일. AGENTS.md나 CLAUDE.md 빠른 시작
워크로그 날짜별 작업 기록. 세션이 시작할 때 읽고 끝날 때 씁니다 매뉴얼 20
하네스 세션이 매일 같은 기준으로 돌게 하는 장치 묶음. 워크로그, 훅, 메모리 등 매뉴얼 20
훅 세션 시작이나 커밋 직전처럼 정해진 순간에 자동으로 도는 검사 매뉴얼 20
워크트리 같은 레포를 따로 여는 작업 폴더. 세션 여럿이 서로의 변경을 건드리지 않게 합니다 매뉴얼 20

감사 파일 전체를 훑어 기준과 다른 곳을 찾는 일. 고치기 전에 목록부터 봅니다 매뉴얼 21
「0건」 감사 결과가 0으로 나온 것. 없다는 뜻인지 범위를 잘못 잡았다는 뜻인지 먼저 가립니다 사례 「0건과 결함 3곳」

개발 용어

말 뜻 디자이너가 볼 때
PR (Pull Request) 변경을 본 코드에 넣기 전에 올리는 검토 요청. 무엇을 왜 바꿨는지, 자동 검사 결과, 리뷰 의견이 한곳에 모입니다 변경 제안서이자 리뷰 공간
머지 (Merge) 검토를 마친 PR을 본 코드에 합치는 일 여기서부터 다른 사람의 작업에도 반영됩니다
CI PR이 올라오면 기계가 먼저 돌리는 자동 검사. 빌드, 타입, 테스트, 스토리북 생성 등을 확인합니다 사람이 보기 전의 안전 점검
GitHub Actions · Workflow · Check CI를 돌리는 도구, 그 안의 단계 묶음, 단계 하나하나의 결과 PR 화면의 초록 체크가 모두 통과면 기본 검사는 끝
Build 작성한 코드를 앱, 패키지, 스토리북 같은 결과물로 만드는 과정 디자인 파일을 export하는 것과 비슷합니다
Storybook 컴포넌트를 앱과 떼어 상태별로 띄워 보는 화면. 기본, 비활성, 로딩, 긴 텍스트, 다크모드를 한 화면에서 비교합니다 코드로 만든 디자인 시스템을 검수하는 캔버스
Visual QA 실제 코드로 구현된 화면이 의도대로 보이는지 확인하는 일 피그마가 아니라 구현 결과를 본다는 점이 다릅니다
Chromatic · Visual Diff 스토리북 화면을 캡처해 이전 버전과 비교하는 도구, 그리고 그 차이 의도한 차이면 승인, 의도하지 않은 차이면 수정
Approve 변경을 확인하고 괜찮다고 승인하는 것. PR에서는 코드를, Chromatic에서는 시각 변화를 승인합니다 무엇을 승인하는지 구분합니다
Changeset 패키지를 배포할 때 변경 내용과 버전을 얼마나 올릴지 적는 기록. patch는 작은 수정, minor는 새 기능이나 variant, major는 기존 사용법이 깨지는 변경 내 변경이 어느 수준인지 알려 줘야 합니다
Breaking Change 기존에 쓰던 방식이 깨질 수 있는 변경. prop 이름이 바뀌거나 토큰이 지워지는 경우 기존 화면에 영향이 가는 큰 변경
Canary · Latest 정식 배포 전에 먼저 설치해 보는 미리보기 버전, 그리고 기본으로 받는 정식 최신 버전 새 컴포넌트를 미리 확인할 때 Canary
Token 색, 간격, 둥근 정도 같은 디자인 값을 #4338CA 대신 color.action.primary.bg처럼 이름으로 관리하는 방식 값이 바뀌어도 이름을 쓴 곳은 한 번에 바뀝니다
Figma Evidence 피그마에서 확인한 시각 근거. 계약과 토큰으로 정리돼야 구현 기준이 됩니다 피그마 값 그대로가 곧 구현 기준은 아닙니다
Sync 피그마, 코드, 스토리북, 워크로그가 서로 다른 말을 하지 않게 다시 맞추는 일 한쪽을 고쳤으면 다른 쪽도 맞췄는지 확인

계약(Contract)과 정본(Source of Truth)은 위 「이 위키에서 쓰는 말」 표에 있습니다.
